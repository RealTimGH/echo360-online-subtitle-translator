# 混合翻译多级优先级：调研与实现规则

调研日期：2026-09-18。

## 行业做法与采用范围

| 来源 | 官方机制 | 本项目采用方式 |
| --- | --- | --- |
| [Azure API Management 后端池](https://learn.microsoft.com/en-us/azure/api-management/backends) | 按优先级分组，同级可按权重分流；高优先级后端全部因熔断不可用时才使用低优先级 | 分组顺序、服务权重与健康状态分别管理；失败改派优先选择较高级别 |
| [LiteLLM Router](https://docs.litellm.ai/docs/routing) | `order` 数值越小优先级越高，同级应用路由策略；失败按顺序升级，另有权重、重试和冷却配置 | 区分首次分配和故障改派，保留现有按服务隔离、部分成功保留和熔断机制 |
| [Envoy Priority levels](https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/upstream/load_balancing/priority) | 根据各级健康容量分配流量，较高优先级容量不足时流量进入后续级别 | 参考“优先级层”和“层内分配”分离的结构；不引入健康容量估算 |
| [Google Cloud Translation quotas](https://docs.cloud.google.com/translate/quotas) | 按内容字符量和请求速率等限制使用量；可以调整配额控制支出 | 字幕 cue 阈值仅是任务路由条件，不能冒充服务额度或金额上限；原有请求限流继续生效 |

行业没有统一的“字幕超过 N 条启用下一组”标准。本项目按用户确认采用**累计启用**，不是服务故障时无条件进入下一级，也不是字幕前 N 条和后 N 条分别交给不同服务。Google Cloud 的官方 API 配额也不适用于本项目使用的非官方 Google 网页端点。

## 行为契约

- `mixedPriorityEnabled` 默认 `false`，未配置或关闭时继续使用原有全体服务加权并行、失败改派逻辑，仍要求至少两个兼容服务。
- `mixedPriorityGroups` 是按优先级排列的 `{ id, afterCues }` 数组；`mixedProviders` 的 `priorityGroup` 关联稳定的组 ID。
- 开启时允许 1–8 级，每级可以有一个或多个服务，同一服务只属于一个组。第一级 `afterCues = 0`，默认参与；其余级别填写严格递增的正整数阈值。
- 按整份字幕中带时间轴且含文本的 cue 总数判断。一个 cue 的多行文本仍算一条；不计请求批次数、文本行数或完成进度。
- 只有总数 **大于** `afterCues` 才启用该级。首次分配在所有已启用级别的兼容服务之间按原有权重进行，字幕不重复分配。
- 未达到阈值的服务不参与请求、后端启动或故障改派。失败字幕只在当前允许的服务池内改派，优先较高级别，再比较原有健康状态、负载和权重。已成功字幕不重新发送。
- 第一级没有兼容服务时提示配置错误，不把下一级静默提升为默认组。设置页保存时校验每一级都有当前可用的已选服务。
- 上移／下移交换整组服务，阈值留在对应级别；删除组前需将已选服务移出，避免丢失归属。关闭功能保留分组草稿，再开启可以继续使用。
- 有效分级配置进入外层译文缓存签名，改变启用状态、组顺序、归属或阈值会使原缓存失效。关闭时不因分组草稿变化而改变路由或缓存。

## 示例

第一级 Google 权重 60、DeepL 权重 40；第二级 Azure 权重 50，阈值 500；第三级 Gemini 权重 50，阈值 1,500。

| 总字幕条数 | 首次分配服务 | 目标比例 |
| --- | --- | --- |
| 1–500 | Google、DeepL | 60% / 40% |
| 501–1,500 | Google、DeepL、Azure | 40% / 26.7% / 33.3% |
| 1,501 及以上 | Google、DeepL、Azure、Gemini | 30% / 20% / 25% / 25% |

比例受离散 cue 数和故障改派影响，是长期目标比例，不能保证每个短任务都精确一致。

## 验证重点

阈值等于和超过的边界、多行 cue、三级累计分流、同级多服务、单服务默认级别、非法／缺失分组与阈值、语言不兼容、阈值外服务禁止故障接管、组顺序与缓存失效、设置保存与恢复、关闭后兼容原有逻辑。自动测试使用模拟翻译服务，不消耗真实 API 额度。
