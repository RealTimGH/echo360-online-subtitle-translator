# 手动 AI 翻译：故障分析与实测记录

日期：2026-09-11。范围：手动导出、提示、导入、补译和本地进度。直连及后端翻译实现没有在本次任务中修改。

## 输入与直接原因

用户提供的 Spatial Analytics v2 输入和输出各有 1522 个 ID，会话一致。输出目录相邻的 `work/build_translation.py` 明确显示：

- 第 7–8 行定义词典（例如 right → 正确/右侧）；
- 第 14–15 行用正则逐词替换；
- 第 16 行删除英文停用词，包含否定句中的助动词；
- 第 20 行对全部 cue 执行该函数；
- 第 22–25 行仅验证结构、条目数和数字/标记存在。

脚本没有模型/API 翻译调用。没有理由把该脚本产物当成模型正常执行翻译后的质量测评，也不能据此推断是 JSON 本身导致模型翻译能力不足。

去除重复标记后的统计：

| 指标 | 数量 |
|---|---:|
| 中英混杂 | 1071 / 1522（70.4%） |
| 没有汉字 | 243 / 1522（16.0%） |
| 包含“正确/右侧” | 86 |
| 包含“……” | 197 |
| 去标记与空白后等于源文本 | 77 |

混合文本、没有汉字本身不是错误证明：代码、名称和缩写可能必须保留。此处的直接证据是脚本实现与大量明确不可读的结果相互吻合。典型危害包括 `can't afford to not understand` 被处理成 `你可以't afford not 理解`，已经涉及否定和句意。

## 新流程的实际 Luna medium 试验

使用 `gpt-5.6-luna`，推理级别 `medium`，新上下文执行连续 78 条实际源文本（c001357–c001434）。模型只拿到新材料，不读取旧结果或实现。它自行撰写 JSON，未被要求用脚本生成翻译。

本实验只测语言输出与导入协议。用户附件是 v2 JSON，没有真实 VTT 时间码，测试夹具使用合成等间距时间码和说话人标签来调用导出器；这些没有发送给模型。实际播放时间轴完整性另由 VTT 回归测试验证。按此文本夹具，全课在 80 条/4000 字符上限下分为 20 批；真实 VTT 停顿可能使边界稍有变化。

1. 第一轮返回全部 78 个 ID，无重复或错误会话。
2. 人工检查发现 c001368（here.）只返回一个句号；c001387 保留了 `0.8 million`。将“标点空壳”和“数字后未译数量级”加入本地检查与提示。
3. 76 条接受并保留，程序只导出其余 2 条的修复材料。
4. 同一 Luna medium 返回 `这里。` 和 `将近一百万人，其中约有 0.8 百万人`；2 条通过检查，78 条全部得到接受。

| 源文片段 | 旧脚本输出 | Luna medium 新输出 |
|---|---|---|
| But this is what you don't want, right? | 这是 what 不要 want, 正确/右侧? | 但这不是你想要的结果，对吧？ |
| not have income. | not income. | 没有收入。 |
| AI can do the job. | AI job. | AI 可以完成这项工作。 |
| This is dumb because rubbish in, rubbish out. | 这是 dumb rubbish 在……中, rubbish out. | 这很愚蠢，因为输入垃圾，输出垃圾。 |

同一 78 条中，中英混杂从旧脚本的 57 条降到 8 条；新结果多为 AI、未能确定的名称等保留词。该计数不能转化为翻译准确率。

仍然存在局限：`can't afford to not understand / how to work effectively with AI` 被译成“我发现你们承担不起不去了解 / 如何有效地使用 AI。”，保留了否定方向，但中文仍然生硬；`tech rate framework` 来源不明确，模型选择保留原词。原音不可用时，不能保证所有听写纠正正确。

这是一次开发过程中的真实模型验证，过程中根据观察补充了检查；不是盲测、全课重译或对所有弱模型的普适质量保证。它验证了小批直接翻译、保留结果和局部补译的可行性。不能把 78 条通过机器检查等同于 78 条均已通过专业译审。

随后用同一 `gpt-5.6-luna` medium 尝试了整份 1522 cue 文件任务。文件助手在结构上可以持续 `next → accept → finish`，但模型在没有平台报错的情况下自行停在 478/1522；扩展没有把这份部分结果当成完整译文。这个结果决定了产品层的取舍：默认仍提供“一次上传任务文件”的低操作成本，但恢复为一个尽量精简的完整 JSON，让模型直接处理全课并返回一个结果文件；提示词只包含任务规则和条数，字幕正文只在下载文件中出现一次，避免重复占用上下文。扩展在本地严格检查 JSON 语法、完整 ID 集合、标签/字面值、数字和明显语言缺陷，仍保留逐批按钮，并把任何中途停止都变成可恢复进度，而不是对 Luna medium 做不真实的“一轮必完成”承诺。最终选择单个 `.translated.json` 作为回传文件，因为扩展可直接导入。

## 行业依据与实施取舍

详细链接见 [协议研究依据](manual-ai-translation-protocol.md#研究依据)。采用的核心做法是：恢复语境而不重分配时间轴；真正限制当前请求规模；少量高质量示例；名词和代码保留不等于逐词词典替换；将结构、准确性、术语和流畅度分开检查；只重试失败条目。

没有增加额外翻译 API、付费服务、后台自动调用或自动把字幕发送给第三方。用户仍然选择 AI；完整文件模式只需手动传递一次精简 JSON 和说明，无法一次处理整课时再使用逐批模式。翻译仍必须由模型直接完成。
